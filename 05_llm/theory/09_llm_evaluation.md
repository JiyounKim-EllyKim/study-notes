# LLM Evaluation 개념 정리

## 1. LLM Evaluation

LLM Evaluation은 LLM의 출력이 사용자의 목적에 맞게 좋은 답변인지 평가하는 과정이다.

일반적인 머신러닝 모델은 정답 라벨과 예측값을 비교해 평가할 수 있지만, LLM은 생성 결과가 다양하고 정답이 하나로 정해지지 않는 경우가 많다.

따라서 LLM 평가는 단순 정확도뿐만 아니라 답변의 유용성, 정확성, 근거 충실성, 안전성, 형식 준수 여부 등을 함께 확인해야 한다.

---

## 2. LLM Evaluation이 필요한 이유

LLM은 자연스러운 답변을 생성할 수 있지만, 항상 정확하거나 신뢰할 수 있는 것은 아니다.

LLM Evaluation은 다음을 확인하기 위해 필요하다.

- 답변이 정확한가?
- 사용자의 질문에 직접 답했는가?
- Prompt 지시를 잘 따랐는가?
- 근거 문서에 충실한가?
- Hallucination이 없는가?
- 출력 형식이 일정한가?
- 안전하지 않은 답변을 생성하지 않는가?
- 실제 서비스에서 사용할 수 있는 품질인가?

---

## 3. 전통적인 모델 평가와 LLM 평가의 차이

| 구분 | 전통적인 ML 평가 | LLM 평가 |
|---|---|---|
| 출력 | 숫자, 라벨, 확률 | 자연어 답변 |
| 정답 | 비교적 명확 | 여러 정답 가능 |
| 평가 기준 | Accuracy, F1-score 등 | 정확성, 유용성, 근거성, 안전성 등 |
| 평가 방식 | 정량 평가 중심 | 정량 평가 + 정성 평가 |
| 어려움 | 데이터 분포, 일반화 | 의미 평가, Hallucination, 주관성 |

LLM 평가는 정답과 완전히 일치하는지만 보는 것이 아니라, 답변이 실제로 도움이 되는지도 함께 봐야 한다.

---

## 4. LLM Evaluation의 주요 평가 기준

LLM 답변을 평가할 때 자주 사용하는 기준은 다음과 같다.

| 기준 | 설명 |
|---|---|
| Correctness | 내용이 사실적으로 맞는가 |
| Relevance | 질문과 관련 있는 답변인가 |
| Completeness | 필요한 내용을 충분히 포함했는가 |
| Faithfulness | 제공된 근거에 충실한가 |
| Helpfulness | 사용자에게 실제로 도움이 되는가 |
| Coherence | 논리적으로 자연스러운가 |
| Conciseness | 불필요하게 장황하지 않은가 |
| Safety | 유해하거나 부적절하지 않은가 |
| Format Following | 요구한 출력 형식을 지켰는가 |

---

## 5. Correctness

Correctness는 답변이 사실적으로 맞는지를 평가하는 기준이다.

LLM은 문장을 자연스럽게 만들 수 있지만, 틀린 내용을 그럴듯하게 말할 수 있다.

```text id="z6msyv"
질문:
RAG는 무엇인가?

좋은 답변:
RAG는 외부 문서를 검색해 LLM의 답변 생성에 활용하는 방식이다.

나쁜 답변:
RAG는 모델을 처음부터 다시 학습시키는 방법이다.
```

Correctness는 특히 금융, 법률, 의료, 채용, 기술 문서처럼 정확성이 중요한 분야에서 매우 중요하다.

---

## 6. Relevance

Relevance는 답변이 사용자의 질문과 얼마나 관련 있는지를 평가한다.

답변이 사실적으로 맞더라도 질문과 직접 관련이 없으면 좋은 답변이라고 보기 어렵다.

```text id="c0lfjr"
질문:
Vector DB는 RAG에서 어떤 역할을 해?

관련 있는 답변:
Embedding Vector를 저장하고, 질문과 유사한 문서 Chunk를 검색하는 역할을 한다.

관련성이 낮은 답변:
RAG는 LLM의 Hallucination을 줄이는 데 도움이 된다.
```

두 번째 답변도 틀린 말은 아니지만, 질문에 직접 답하지 못한다.

---

## 7. Completeness

Completeness는 답변이 필요한 내용을 충분히 포함했는지를 평가한다.

너무 짧거나 핵심 요소가 빠진 답변은 완전성이 낮다.

예를 들어 RAG의 흐름을 설명하라는 질문에 “문서를 검색해서 답변하는 방식”이라고만 답하면 핵심은 맞지만 충분하지 않을 수 있다.

좋은 답변은 필요한 구성 요소와 흐름을 함께 포함해야 한다.

---

## 8. Faithfulness

Faithfulness는 답변이 제공된 근거 문서에 충실한지를 평가하는 기준이다.

RAG 시스템에서는 LLM이 검색된 문서에 없는 내용을 추가하지 않아야 한다.

```text id="r5socd"
검색 문서:
Career.zip은 AI 모의면접 서비스이다.

답변:
Career.zip은 AI 모의면접 서비스이며, 사용자는 JD와 이력서를 기반으로 질문을 받을 수 있다.
```

만약 검색 문서에 JD와 이력서 기반 질문 생성 내용이 없다면, 답변의 일부는 근거에 충실하지 않은 것이다.

---

## 9. Helpfulness

Helpfulness는 답변이 사용자에게 실제로 도움이 되는지를 평가한다.

정확한 답변이라도 너무 추상적이거나 사용자의 상황을 반영하지 못하면 도움이 적을 수 있다.

### 도움이 되는 답변의 특징

- 질문에 직접 답한다.
- 사용자의 목적에 맞다.
- 필요한 수준의 구체성을 가진다.
- 다음 행동을 결정하는 데 도움이 된다.
- 불확실한 부분을 명확히 표시한다.

---

## 10. Format Following

Format Following은 모델이 요청한 출력 형식을 잘 지켰는지를 평가한다.

LLM 애플리케이션에서는 답변 내용뿐만 아니라 형식이 중요한 경우가 많다.

```text id="v9libp"
요청:
JSON 형식으로 출력해줘.

원하는 출력:
{
  "label": "positive",
  "reason": "배송이 빠르다는 긍정 표현이 있음"
}
```

모델이 JSON이 아닌 일반 문장으로 답하면 내용이 맞더라도 형식 준수에는 실패한 것이다.

---

## 11. Safety

Safety는 모델이 유해하거나 부적절한 답변을 생성하지 않는지 평가하는 기준이다.

LLM 서비스에서는 정확성뿐만 아니라 안전성도 중요하다.

### 확인할 점

- 개인정보를 노출하지 않는가?
- 위험한 행동을 유도하지 않는가?
- 차별적이거나 혐오적인 표현이 없는가?
- 민감한 주제에서 과도하게 단정하지 않는가?
- 사용자가 오해할 수 있는 위험한 정보를 제공하지 않는가?

---

## 12. 평가 방식의 종류

LLM Evaluation은 크게 세 가지 방식으로 나눌 수 있다.

| 방식 | 설명 |
|---|---|
| Human Evaluation | 사람이 직접 답변을 평가 |
| Automatic Evaluation | 지표나 규칙으로 자동 평가 |
| LLM-as-a-Judge | 다른 LLM을 평가자로 사용 |

실제 서비스에서는 한 가지 방식만 사용하기보다 여러 방식을 함께 사용하는 경우가 많다.

---

## 13. Human Evaluation

Human Evaluation은 사람이 직접 LLM 답변을 읽고 평가하는 방식이다.

자동 평가로는 답변의 자연스러움, 유용성, 맥락 적합성 등을 완벽하게 판단하기 어렵기 때문에 사람 평가가 중요하다.

### 장점

- 의미와 맥락을 깊게 평가할 수 있다.
- 실제 사용자 관점의 유용성을 확인할 수 있다.
- 복잡한 오류를 발견할 수 있다.

### 한계

- 시간과 비용이 많이 든다.
- 평가자마다 기준이 다를 수 있다.
- 대량 평가가 어렵다.
- 평가 기준을 명확히 정해야 한다.

---

## 14. Rubric

Rubric은 평가 기준을 명확하게 정의한 채점표이다.

LLM 답변을 사람이 평가할 때는 평가자의 주관을 줄이기 위해 Rubric을 만드는 것이 좋다.

| 점수 | 기준 예시 |
|---:|---|
| 5점 | 정확하고, 질문에 직접 답하며, 근거가 충분함 |
| 4점 | 대부분 정확하지만 일부 설명이 부족함 |
| 3점 | 핵심은 맞지만 누락이나 모호함이 있음 |
| 2점 | 일부만 맞고 중요한 오류가 있음 |
| 1점 | 질문에 답하지 못하거나 대부분 틀림 |

Rubric이 명확해야 평가 결과를 비교하고 개선 방향을 찾기 쉽다.

---

## 15. Automatic Evaluation

Automatic Evaluation은 규칙, 지표, 코드 등을 사용해 모델 출력을 자동으로 평가하는 방식이다.

### 예시

- 정답 라벨과 비교
- 특정 키워드 포함 여부 확인
- JSON 형식 유효성 검사
- 길이 제한 준수 여부 확인
- 금지어 포함 여부 확인
- BLEU, ROUGE 같은 텍스트 유사도 지표 계산

자동 평가는 빠르고 대량으로 수행할 수 있지만, 의미 품질을 완벽하게 평가하기는 어렵다.

---

## 16. LLM-as-a-Judge

LLM-as-a-Judge는 LLM을 평가자로 사용해 다른 LLM의 답변을 평가하는 방식이다.

예를 들어 평가용 LLM에게 질문, 정답 또는 기준, 모델 답변을 주고 점수와 이유를 출력하게 할 수 있다.

```text id="mxnh9c"
입력:
- 사용자 질문
- 참고 정답
- 모델 답변
- 평가 기준

출력:
- 점수
- 평가 이유
- 오류 유형
```

LLM-as-a-Judge는 사람 평가보다 빠르지만, 평가자 LLM도 편향이나 오류를 가질 수 있다.

---

## 17. LLM-as-a-Judge 사용 시 주의할 점

LLM 평가자를 사용할 때는 다음을 주의해야 한다.

- 평가 기준을 명확히 제공해야 한다.
- 점수만 받지 말고 평가 이유도 함께 확인한다.
- 사람 평가와 일부 비교하여 신뢰도를 확인한다.
- 평가자 모델이 특정 답변 스타일을 선호할 수 있다.
- 긴 답변을 더 좋게 평가하는 편향이 있을 수 있다.
- 평가 결과를 절대적인 정답으로 보지 않는다.

---

## 18. Pairwise Evaluation

Pairwise Evaluation은 두 개의 답변을 비교하여 어느 쪽이 더 나은지 평가하는 방식이다.

```text id="uqa0yk"
질문:
RAG의 장점을 설명해줘.

답변 A:
...

답변 B:
...

평가:
A와 B 중 더 나은 답변 선택
```

점수를 직접 매기는 것보다 두 답변을 비교하는 방식이 더 안정적인 경우가 있다.

모델 버전 비교나 Prompt A/B Test에 유용하다.

---

## 19. Reference-based Evaluation

Reference-based Evaluation은 정답 또는 모범 답변과 모델 출력을 비교하는 방식이다.

분류, 추출, 짧은 질의응답처럼 정답이 비교적 명확한 작업에서 사용할 수 있다.

### 예시

- 감성 분석 라벨 비교
- 개체명 추출 결과 비교
- 정답 문장과의 유사도 비교
- 필수 키워드 포함 여부 확인

하지만 생성형 답변은 정답 표현이 다양할 수 있어 단순 문자열 비교만으로는 부족하다.

---

## 20. Reference-free Evaluation

Reference-free Evaluation은 별도의 정답 없이 답변 자체의 품질을 평가하는 방식이다.

예를 들어 답변이 질문에 관련 있는지, 논리적으로 자연스러운지, 안전한지 등을 평가한다.

### 사용 상황

- 정답이 하나로 정해지지 않는 질문
- 창의적 글쓰기
- 요약 품질 평가
- 상담 답변 평가
- 문서 기반 답변의 유용성 평가

Reference-free Evaluation은 사람 평가나 LLM-as-a-Judge와 함께 사용되는 경우가 많다.

---

## 21. Task-specific Evaluation

LLM은 다양한 작업에 사용되므로 작업별로 평가 기준이 달라져야 한다.

| 작업 | 평가 기준 |
|---|---|
| 요약 | 핵심 포함, 간결성, 사실 보존 |
| 질의응답 | 정확성, 관련성, 근거성 |
| 분류 | Accuracy, F1-score |
| 정보 추출 | Precision, Recall, F1-score |
| RAG | 검색 품질, 근거 충실성, 출처 정확성 |
| 코드 생성 | 실행 여부, 테스트 통과, 요구사항 충족 |
| Agent | Tool 선택, 실행 과정, 목표 달성 |

작업 목적과 평가 기준이 맞지 않으면 잘못된 결론을 내릴 수 있다.

---

## 22. RAG Evaluation

RAG 시스템은 검색 Retrieval과 생성 Generation이 결합된 구조이므로, 평가도 나누어 보는 것이 좋다.

| 평가 대상 | 확인할 점 |
|---|---|
| Retrieval | 관련 문서를 잘 검색했는가 |
| Generation | 검색 문서를 바탕으로 답변했는가 |
| Grounding | 답변이 근거 문서에 충실한가 |
| Citation | 출처가 올바르게 연결되었는가 |
| Helpfulness | 사용자의 질문 해결에 도움이 되는가 |

RAG 답변이 틀렸을 때는 검색이 문제인지, 생성이 문제인지 구분해야 한다.

---

## 23. Retrieval 평가 지표

RAG에서 검색 단계는 Information Retrieval 지표로 평가할 수 있다.

| 지표 | 설명 |
|---|---|
| Recall@k | 정답 문서가 상위 k개 안에 포함되었는지 |
| Precision@k | 상위 k개 문서 중 관련 문서 비율 |
| MRR | 정답 문서가 처음 등장한 순위 평가 |
| NDCG | 순위와 관련도를 함께 고려 |

검색 단계에서 필요한 문서를 가져오지 못하면, LLM이 아무리 좋아도 정확한 답변을 만들기 어렵다.

---

## 24. Groundedness

Groundedness는 답변이 제공된 근거 문서에 기반하고 있는지를 평가하는 기준이다.

RAG에서 매우 중요한 평가 항목이다.

```text id="ear7wt"
좋은 답변:
검색 문서에 있는 내용을 바탕으로 답변함

나쁜 답변:
검색 문서에 없는 내용을 추가로 생성함
```

Groundedness가 낮으면 Hallucination 가능성이 높다.

---

## 25. Citation Accuracy

Citation Accuracy는 답변에 표시된 출처가 실제 답변 내용을 뒷받침하는지 평가하는 기준이다.

출처가 있다고 해서 항상 좋은 답변은 아니다.

다음과 같은 경우는 Citation 품질이 낮다.

- 출처 문서에 없는 내용을 인용함
- 관련 없는 문서를 출처로 표시함
- 답변 내용과 출처가 연결되지 않음
- 여러 출처 중 일부만 관련 있음

RAG 시스템에서는 답변과 출처가 실제로 일치하는지 확인해야 한다.

---

## 26. Hallucination 평가

Hallucination 평가는 모델이 근거 없는 내용을 생성했는지 확인하는 과정이다.

### 확인할 점

- 답변에 사실 오류가 있는가?
- 제공된 문서에 없는 내용을 추가했는가?
- 불확실한 내용을 단정적으로 말했는가?
- 존재하지 않는 출처를 제시했는가?
- 숫자, 날짜, 이름, 기관명을 잘못 생성했는가?

Hallucination은 사용자가 알아차리기 어려울 정도로 자연스럽게 나타날 수 있으므로 별도 평가가 필요하다.

---

## 27. Instruction Following 평가

Instruction Following은 모델이 사용자의 지시를 얼마나 잘 따랐는지 평가하는 기준이다.

### 예시

```text id="pdlm95"
요청:
3줄 이내로 요약해줘.

실패:
10줄로 길게 답변함
```

내용이 맞더라도 지시한 형식이나 제약을 지키지 않으면 좋은 답변이라고 보기 어렵다.

---

## 28. Consistency 평가

Consistency는 같은 입력이나 비슷한 입력에 대해 모델이 일관된 답변을 하는지 평가하는 기준이다.

LLM은 확률적으로 답변을 생성하므로, 같은 질문에도 조금씩 다른 답을 할 수 있다.

### 확인할 점

- 같은 질문에 대해 핵심 답변이 유지되는가?
- 비슷한 질문에 대해 서로 모순된 답을 하지 않는가?
- 서비스 정책이나 라벨 기준을 일관되게 적용하는가?
- 출력 형식이 매번 유지되는가?

---

## 29. Robustness 평가

Robustness는 모델이 다양한 입력 상황에서도 안정적으로 작동하는지 평가하는 기준이다.

### 평가할 입력 예시

- 오타가 있는 질문
- 매우 짧은 질문
- 모호한 질문
- 긴 문서
- 불완전한 입력
- Prompt Injection 시도
- 예상하지 못한 형식의 입력
- 도메인 밖 질문

Robustness가 낮으면 실제 사용자 환경에서 쉽게 실패할 수 있다.

---

## 30. Evaluation Dataset

Evaluation Dataset은 LLM 성능을 평가하기 위해 준비한 테스트 데이터이다.

좋은 Evaluation Dataset은 실제 사용 상황을 잘 반영해야 한다.

### 포함하면 좋은 데이터

- 자주 들어오는 질문
- 어려운 질문
- 모호한 질문
- 도메인 특화 질문
- 정답이 명확한 질문
- 모델이 자주 틀리는 질문
- 안전성 검사가 필요한 질문
- 형식 준수가 중요한 질문

---

## 31. Golden Dataset

Golden Dataset은 사람이 검수한 고품질 평가 데이터셋이다.

질문, 기대 답변, 평가 기준, 관련 문서 등이 포함될 수 있다.

```text id="oqhzyk"
Question:
RAG의 장점은 무엇인가?

Expected Answer:
외부 문서를 검색해 답변에 활용할 수 있으며,
최신 정보나 사내 문서 기반 답변에 유용하고,
Hallucination을 줄이는 데 도움이 된다.
```

Golden Dataset은 모델 버전 비교와 회귀 테스트에 유용하다.

---

## 32. Regression Test

Regression Test는 모델이나 Prompt를 수정한 뒤 기존에 잘 되던 기능이 망가지지 않았는지 확인하는 테스트이다.

LLM 서비스에서는 Prompt 하나를 바꿔도 출력이 크게 달라질 수 있다.

따라서 변경 전후를 비교하는 테스트가 필요하다.

### 확인할 점

- 기존 질문에 대한 답변 품질이 유지되는가?
- 출력 형식이 깨지지 않았는가?
- Hallucination이 늘지 않았는가?
- 특정 케이스에서 성능이 떨어지지 않았는가?
- 비용이나 응답 시간이 과도하게 증가하지 않았는가?

---

## 33. A/B Test

A/B Test는 두 가지 모델, Prompt, RAG 설정 등을 비교하는 방법이다.

예를 들어 Prompt A와 Prompt B 중 어떤 것이 더 좋은 답변을 만드는지 비교할 수 있다.

```text id="rwpnkt"
Prompt A:
간단한 지시만 포함

Prompt B:
역할, 조건, 출력 형식 포함

비교:
정확성, 유용성, 형식 준수율
```

A/B Test는 실제 사용자 반응이나 평가 점수를 비교할 때 유용하다.

---

## 34. Online Evaluation과 Offline Evaluation

| 구분 | 설명 |
|---|---|
| Offline Evaluation | 미리 준비한 평가 데이터셋으로 테스트 |
| Online Evaluation | 실제 사용자 환경에서 성능을 관찰 |

Offline Evaluation은 배포 전에 안정성을 확인하는 데 유용하다.

Online Evaluation은 실제 사용자 행동과 만족도를 확인하는 데 필요하다.

둘을 함께 사용해야 모델 품질을 지속적으로 관리할 수 있다.

---

## 35. Monitoring

Monitoring은 배포된 LLM 시스템의 성능과 오류를 지속적으로 관찰하는 과정이다.

LLM은 데이터, 사용자 질문, 외부 문서, 모델 버전이 바뀌면서 품질이 달라질 수 있다.

### 모니터링 항목

- 응답 성공률
- 오류 발생률
- 응답 시간
- 비용
- 사용자 피드백
- Hallucination 의심 사례
- 안전성 위반 사례
- 검색 실패 사례
- 출력 형식 오류

---

## 36. Cost와 Latency 평가

LLM 서비스에서는 답변 품질뿐만 아니라 비용과 응답 시간도 중요하다.

| 항목 | 설명 |
|---|---|
| Cost | 모델 호출 비용, 토큰 사용량, 검색 비용 |
| Latency | 사용자가 답변을 받기까지 걸리는 시간 |
| Throughput | 일정 시간 동안 처리 가능한 요청 수 |

좋은 답변을 만들더라도 너무 비싸거나 느리면 실제 서비스에 적용하기 어렵다.

---

## 37. Error Analysis

Error Analysis는 모델이 틀린 사례를 직접 분석하는 과정이다.

LLM Evaluation에서 점수만 보는 것보다 오류 사례를 읽고 원인을 분류하는 것이 중요하다.

### 오류 유형 예시

- 질문 의도 오해
- 근거 문서 검색 실패
- 검색 문서 오해
- Hallucination
- 형식 미준수
- 답변 누락
- 과도하게 장황함
- 안전성 문제
- Tool 사용 오류
- 출처 연결 오류

오류 유형을 분류하면 어떤 부분을 개선해야 하는지 명확해진다.

---

## 38. 평가 결과를 개선에 활용하기

Evaluation은 점수를 내는 것으로 끝나지 않는다.

평가 결과를 바탕으로 시스템을 개선해야 한다.

| 문제 | 개선 방향 |
|---|---|
| 관련 없는 답변 | Prompt 수정, 질문 의도 분석 개선 |
| 근거 없는 답변 | RAG 강화, Grounding 지시 추가 |
| 검색 실패 | Chunking, Embedding, Retriever 개선 |
| 형식 오류 | Output Parser, JSON Schema, 예시 추가 |
| 긴 답변 | 길이 제한, 요약 지시 추가 |
| 안전성 문제 | Guardrail, 필터링, 정책 강화 |
| 느린 응답 | 모델 경량화, 캐싱, 검색 최적화 |

---

## 39. LLM Evaluation 사용 시 주의할 점

- 하나의 점수만으로 모델 품질을 판단하지 않는다.
- 작업 목적에 맞는 평가 기준을 먼저 정해야 한다.
- 정량 평가와 정성 평가를 함께 사용한다.
- 평가 데이터셋은 실제 사용 상황을 반영해야 한다.
- LLM-as-a-Judge 결과를 절대적인 정답으로 보지 않는다.
- RAG는 검색 단계와 생성 단계를 나누어 평가한다.
- Prompt나 모델을 바꿀 때 Regression Test를 수행한다.
- 배포 후에도 Monitoring을 통해 품질을 계속 확인한다.

---

## 40. 정리

- LLM Evaluation은 LLM의 출력이 정확하고 유용하며 안전한지 평가하는 과정이다.
- LLM은 정답이 하나로 정해지지 않는 생성 작업이 많아 평가가 어렵다.
- 주요 평가 기준에는 Correctness, Relevance, Completeness, Faithfulness, Helpfulness, Safety, Format Following이 있다.
- LLM 평가는 Human Evaluation, Automatic Evaluation, LLM-as-a-Judge 방식으로 수행할 수 있다.
- Human Evaluation은 의미와 맥락을 잘 평가할 수 있지만 시간과 비용이 많이 든다.
- LLM-as-a-Judge는 빠르게 평가할 수 있지만 평가자 모델의 편향과 오류를 주의해야 한다.
- Pairwise Evaluation은 두 답변 중 더 나은 답변을 고르는 방식이다.
- RAG Evaluation은 Retrieval, Generation, Grounding, Citation을 나누어 평가해야 한다.
- Hallucination 평가는 근거 없는 내용이나 사실 오류를 찾는 데 중요하다.
- Evaluation Dataset과 Golden Dataset은 모델 비교와 Regression Test에 필요하다.
- 배포 후에는 Monitoring을 통해 실제 사용자 환경에서의 품질을 지속적으로 확인해야 한다.
- LLM Evaluation은 점수 측정이 아니라 시스템 개선을 위한 과정이다.
